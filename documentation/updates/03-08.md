# Changements recents backend

Ce document resume les changements recents ajoutes au backend et les impacts a prendre en compte cote frontend.

## 1. Modification du profil utilisateur

L'utilisateur connecte peut maintenant modifier son profil via :

```text
PATCH /users/
Authorization: Bearer <access_token>
Content-Type: application/json
```

### Modifier le nom et le prenom

Le changement de nom et prenom ne demande pas le mot de passe actuel.

```json
{
  "first_name": "John",
  "last_name": "Doe"
}
```

### Modifier l'email

Le changement d'email se fait maintenant en deux etapes. La demande se fait depuis
le profil, mais l'email du compte n'est pas modifie immediatement.

```json
{
  "email": "new-email@example.com"
}
```

L'email est normalise en minuscules et l'unicite est verifiee de maniere insensible a la casse.

Le backend envoie ensuite un email a l'adresse actuelle du compte. Cet email contient :

```text
- un lien de confirmation vers {FRONTEND_URL}/confirm-email-change?token=...
- un lien de reset password si l'utilisateur n'est pas a l'origine de la demande
```

Apres clic sur le lien de confirmation, le frontend demande le mot de passe actuel
et appelle :

```text
POST /users/email-change/confirm/
```

```json
{
  "token": "...",
  "current_password": "MotDePasseActuel123!"
}
```

Le backend verifie le token, le mot de passe actuel et la disponibilite du nouvel
email avant de modifier reellement `user.email`.

### Modifier le mot de passe

Le changement de mot de passe demande le mot de passe actuel, le nouveau mot de passe et sa confirmation.

```json
{
  "current_password": "MotDePasseActuel123!",
  "password": "NouveauMotDePasse123!",
  "password_confirm": "NouveauMotDePasse123!"
}
```

Le nouveau mot de passe applique les memes regles que l'inscription et le reset password.

### Reponse succes

```json
{
  "message": "Profil mis a jour avec succes",
  "user": {
    "id": "...",
    "email": "current-email@example.com",
    "first_name": "John",
    "last_name": "Doe",
    "is_staff": false,
    "is_active": true,
    "is_two_factor_enabled": false
  }
}
```

Le frontend doit remplacer son utilisateur local par `response.user`.

### Notifications email de securite

Des emails de securite sont maintenant envoyes apres certaines modifications du profil :

```text
Changement de nom/prenom   -> aucun email
Demande de changement email -> email envoye a l'adresse actuelle avec lien de confirmation et lien de reset password
Confirmation changement email -> email envoye a la nouvelle adresse
Changement de mot de passe -> email envoye a l'adresse du compte avant modification avec un lien direct de reset password
```

Ces emails utilisent la configuration email Django existante :

```text
EMAIL_BACKEND
DEFAULT_FROM_EMAIL
EMAIL_HOST
EMAIL_PORT
EMAIL_HOST_USER
EMAIL_HOST_PASSWORD
EMAIL_USE_TLS
EMAIL_USE_SSL
FRONTEND_URL
SUPPORT_EMAIL
```

Si l'envoi email echoue, la mise a jour du profil reste validee et l'erreur est loggee cote serveur.
Le lien de reset password pointe vers `{FRONTEND_URL}/reset-password?uidb64=...&token=...`.
`SUPPORT_EMAIL` vaut `projet.ggs@gmail.com` par defaut et est affiche dans les
emails de securite lorsque l'utilisateur n'est pas a l'origine de l'action.
Les emails sont envoyes en texte et en HTML. Dans la version HTML, les URLs sont
placees derriere des liens lisibles comme `confirmez le changement d'email` ou
`choisissez immediatement un nouveau mot de passe`. La version texte garde l'URL
complete en fallback.

### Erreurs possibles

```text
EMAIL_ALREADY_EXISTS
CURRENT_PASSWORD_REQUIRED
INVALID_CURRENT_PASSWORD
INVALID_EMAIL_CHANGE_TOKEN
EMAIL_CHANGE_TOKEN_EXPIRED
EMAIL_CHANGE_TOKEN_STALE
PASSWORD_FIELDS_REQUIRED
PASSWORD_MISMATCH
WEAK_PASSWORD
```

Pour `WEAK_PASSWORD`, le backend renvoie aussi `details`, une liste de messages a afficher sous le champ mot de passe.

## 2. Double authentification TOTP

La double authentification TOTP a ete ajoutee avec `pyotp`.

Dependency ajoutee :

```text
pyotp==2.9.0
```

Champs ajoutes au modele utilisateur :

```text
totp_secret
is_two_factor_enabled
```

Le serializer utilisateur expose maintenant :

```text
is_two_factor_enabled
```

### Initialiser la 2FA

```text
POST /users/2fa/setup/
Authorization: Bearer <access_token>
```

Reponse :

```json
{
  "message": "Configuration 2FA initialisee",
  "secret": "BASE32SECRET",
  "provisioning_uri": "otpauth://totp/Weeb:user@example.com?secret=BASE32SECRET&issuer=Weeb"
}
```

Le frontend doit transformer `provisioning_uri` en QR code.

### Confirmer et activer la 2FA

```text
POST /users/2fa/confirm/
Authorization: Bearer <access_token>
```

```json
{
  "code": "123456"
}
```

### Desactiver la 2FA

```text
POST /users/2fa/disable/
Authorization: Bearer <access_token>
```

```json
{
  "code": "123456"
}
```

### Login avec 2FA activee

Premier appel :

```text
POST /users/login/
```

```json
{
  "email": "user@example.com",
  "password": "SecurePass123!"
}
```

Si la 2FA est activee, le backend ne renvoie pas encore d'access token :

```json
{
  "message": "Code 2FA requis",
  "requires_2fa": true,
  "two_factor_token": "...",
  "user": {
    "is_two_factor_enabled": true
  }
}
```

Le frontend doit ensuite demander le code a 6 chiffres et appeler :

```text
POST /users/2fa/verify-login/
```

```json
{
  "two_factor_token": "...",
  "code": "123456"
}
```

Si le code est valide, la reponse redevient celle d'un login classique avec `access` et cookie HttpOnly `refresh_token`.

Erreurs possibles :

```text
INVALID_TWO_FACTOR_CODE
TWO_FACTOR_TOKEN_EXPIRED
INVALID_TWO_FACTOR_TOKEN
TWO_FACTOR_ALREADY_ENABLED
TWO_FACTOR_NOT_ENABLED
TWO_FACTOR_SETUP_REQUIRED
```

## 3. Favoris d'articles

Les utilisateurs connectes peuvent ajouter ou retirer des articles de leurs favoris.

Endpoints :

```text
POST   /articles/:slug/favorite/
DELETE /articles/:slug/favorite/
Authorization: Bearer <access_token>
```

Reponse :

```json
{
  "message": "Article ajoute aux favoris",
  "is_favorite": true,
  "favorites_count": 4
}
```

Les reponses article exposent maintenant :

```text
favorites_count
is_favorite
```

Pour un visiteur non connecte, `is_favorite` vaut toujours `false`.

Le profil utilisateur peut aussi lister les articles favoris :

```text
GET /users/me/favorites/
Authorization: Bearer <access_token>
```
